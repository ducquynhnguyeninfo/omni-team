# Adapters — how omni-team plugs into each tool

One canonical source (`team/`, `skills/`), several native formats. [`../install.py`](../install.py) (stdlib only) generates the native files; [`../orchestrator.py`](../orchestrator.py) runs roles headless through any CLI "engine".

## install.py

```bash
python3 .omni-team/install.py [install|init|upgrade|uninstall] [--dir <project>]
                              [--tools claude,codex,gemini,agents-md | all]
                              [--project-root <dir>] [--claude-models deep=opus,standard=sonnet,fast=haiku]
                              [--codex-effort deep=high,standard=medium,fast=low]
                              [--no-pointer] [--force] [--dry-run] [--uninstall]
```

| Option | Effect |
|---|---|
| `--dir <project>` | **vendor** the framework into `<project>/.omni-team/` (fresh copy, or upgrade of an existing copy: framework files replaced/removed, `project/` and `runs/` preserved; downgrade needs `--force`), then register the adapters in `<project>/`. Warns when `<project>` is not a git repository root |
| `--project-root <dir>` | register adapters into `<dir>` without copying anything (the framework is used where it is) |
| neither | register adapters into the folder that contains this `.omni-team/` |
| `init` | alias of `install` |
| `upgrade` | like install, but requires an existing `<project>/.omni-team/` |
| `uninstall` | remove generated adapters and pointer blocks; a vendored folder is left in place |

All checks (foreign files with the same name, a non-omni-team `.omni-team/` folder, downgrade, missing directory) run before anything is written.

| Tool | Generated (relative to project root) | Notes |
|---|---|---|
| `claude` | `.claude/agents/<role>.md` | YAML frontmatter `name`, `description`, `tools` (read-only roles: `Read, Grep, Glob, Bash`; `run` roles inherit all tools incl. MCP), `model` by tier; body = role + protocol |
| | `.claude/skills/<skill>/SKILL.md` | invocable as `/omni-task` etc. |
| | pointer block in `CLAUDE.md` | created if missing |
| `codex` | `.codex/agents/<role>.toml` | `name`, `description`, `model_reasoning_effort` by tier, `sandbox_mode` (`read-only` / `workspace-write`), `developer_instructions` = role + protocol |
| | `.agents/skills/<skill>/SKILL.md` | Codex repo skills |
| | pointer block in `AGENTS.md` | |
| `gemini` | pointer block in `GEMINI.md` | Gemini runs gates via the orchestrator / `prompt` |
| `agents-md` | pointer block in `AGENTS.md` | Cursor, GitHub Copilot, Windsurf, Aider, Zed, Jules, Amp … read `AGENTS.md` |

Safety properties:

- Every generated file contains the marker `generated by omni-team`. The installer overwrites or deletes **only** files with that marker; a same-named file without it aborts the run (use `--force` to overwrite deliberately).
- Pointer blocks are delimited by `<!-- omni-team:begin … -->` / `<!-- omni-team:end -->`; content outside the block is never touched. `--uninstall` removes the block and deletes the file only if nothing else remains.
- Generated files for roles/skills that no longer exist are cleaned up on the next install.
- Re-running is idempotent. Re-run after editing `team/` or `skills/`.

Generated files are build output: edit the sources, never the output. Commit them or git-ignore them as you prefer — `install.py` regenerates them in milliseconds.

## Using a role without installing

Every tool can use the canonical files directly: "Read `.omni-team/team/_protocol.md` and `.omni-team/team/<role>.md`, act as that role for: …". Installing only adds convenience (auto-selection by description, `/skills`, per-role tool/sandbox limits, model per tier).

## Engines (headless)

`orchestrator.py` builds a self-contained prompt (role + protocol + invocation block) and runs it through an argv template from `orchestrator.engines`:

```yaml
orchestrator:
  engine: claude
  engines:
    claude:
      cmd:     ["claude", "-p", "--model", "{tier}", "--allowedTools", "Read,Grep,Glob,Bash(git diff:*),…"]
      cmd_run: ["claude", "-p", "--model", "{tier}", "--allowedTools", "Read,Grep,Glob,Bash,Write(.omni-team/runs/**)"]
      tiers:   { deep: opus, standard: sonnet, fast: haiku }
    codex:
      cmd:     ["codex", "exec", "--sandbox", "read-only", "-c", "model_reasoning_effort=\"{tier}\"", "-"]
      cmd_run: ["codex", "exec", "--sandbox", "workspace-write", "-c", "sandbox_workspace_write.network_access=true", "-c", "model_reasoning_effort=\"{tier}\"", "-"]
      tiers:   { deep: high, standard: medium, fast: low }
```

- The prompt is piped to the CLI's **stdin** by default (no argv length limits; safe with variadic flags like Claude's `--allowedTools`). If a CLI only accepts the prompt as an argument, put `"{prompt}"` as a whole argv element and it is substituted there instead.
- `{tier}` is replaced inside any element by the engine's value for the role's tier.
- `cmd_run` is used for `access: run` roles (`smoke-tester`); it falls back to `cmd`.
- The engine's stdout is the report; a non-zero exit with no verdict line becomes `BLOCKED`.

### Adding an engine

Any CLI that takes a prompt and prints the answer works. Add it in `project/profile.yaml` (merged by name) and select it with `--engine <name>` or `orchestrator.engine`:

```yaml
orchestrator:
  engines:
    gemini:
      cmd: ["gemini", "-m", "{tier}", "-p", "{prompt}"]   # argv form, if the CLI does not read stdin
      tiers: { deep: "<strongest model id>", standard: "<default model id>", fast: "<fast model id>" }
```

Check the CLI's current flags before relying on a template — tools change them often. For a browser-capable smoke run with Claude, add your browser MCP tools (e.g. `mcp__playwright`) to `cmd_run`'s `--allowedTools`.
